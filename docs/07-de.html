Apache Airflow：ETL 的排程指揮官

Airflow 是一個工作流程排程工具，用 Python 定義任務（Task）和任務之間的依賴關係（DAG）。

📋 DAG（有向無環圖）

DAG 定義了一個完整的 ETL 工作流程：任務有哪些、執行順序是什麼、失敗了怎麼辦。每個圖表通常對應一個 DAG。

⏱️ Cron 排程

每個 DAG 有執行頻率設定，如 */5 * * * *（每5分鐘）或 @daily（每天），Airflow 自動在對應時間執行。

一個 DAG 的任務流程（視覺化）

範例：每日人口資料更新 DAG
① 提取資料 → ② 清洗驗證 → ③ 地址轉換 → ④ 寫入資料庫 → ⑤ 清理暫存
任務 ②③ 可以並行執行（Airflow 會自動判斷依賴關係）
任何步驟失敗 → Airflow 自動重試、發警告通知

Celery：讓多個任務同時跑

Airflow 搭配 Celery 做分散式任務執行。Celery 是一個任務佇列系統：

# 架構說明
Airflow Scheduler # 排程器：決定什麼時候執行什麼任務
    ↓ 把任務放進佇列
Redis (Broker) # 訊息代理：任務佇列
    ↓ 通知 Worker 有新任務
Celery Workers # 多個 Worker 並行處理任務
    ↓ 執行完成
PostgreSQL # 寫入結果
💡 類比：Celery 就像「訂單管理系統」。Airflow 是發出訂單的客服中心，Redis 是放訂單的收件盒，多個 Celery Worker 是不同的工作人員，各自從收件盒拿一張訂單去處理，所以多個任務可以同時進行。

自動佇列路由（智能設計）

系統根據 DAG 的執行頻率自動決定放進哪個佇列——這是避免「重要的即時任務被慢的批次任務阻塞」的設計：

排程頻率 佇列 說明
*/5 * * * *（10分鐘內） realtime 即時資料，需要快速執行
0 * * * *（每小時/每天） default 一般資料更新任務
@monthly（每月以上） heavy 大量資料批次處理

ETL 各階段的工具

📡 Extract（提取工具）

  • → extract_stage.py
  • → TDX API（交通資料）
  • → CHT API（電信資料）
  • → 政府開放資料
  • → 支援 HTTP/HTTPS

🔧 Transform（轉換工具）

  • → 資料型態轉換
  • → transform_address.py
  • → 地址→經緯度轉換
  • → 空值處理和清洗
  • → 統計計算（平均、加總）

🗄️ Load（載入工具）

  • → load_stage.py
  • → UPSERT（插入或更新）
  • → 批次寫入優化
  • → 事務控制
  • → 失敗回滾

資料從 API 到圖表的完整範例

# 範例：每小時更新捷運乘客數

# Step 1: Extract - 呼叫 TDX API
response = requests.get(
  "https://tdx.transportdata.tw/api/basic/v2/Rail/Metro/...",
  headers={"Authorization": tdx_token}
)
raw_data = response.json()

# Step 2: Transform - 清洗整理
cleaned = []
for station in raw_data:
  if station["StationName"] and station["OnDemand"] > 0:
    cleaned.append({
      "station_name": station["StationName"]["Zh_tw"],
      "count": station["OnDemand"],
      "timestamp": datetime.now()
    })

# Step 3: Load - 寫入資料庫
conn.execute(
  "INSERT INTO mrt_ridership (station_name, count, timestamp) VALUES ...",
  cleaned
)
conn.commit()
💡 DE 和後端的分工為什麼這樣設計？
資料工程（Python）和後端（Go）各有強項：Python 有豐富的資料處理生態（pandas, numpy），適合 ETL；Go 追求高效能和低延遲，適合 API 伺服器。讓每個工具做最擅長的事，是工程上的好設計。
