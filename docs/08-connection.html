🔗 前後端如何連接

從使用者按下按鈕，到圖表出現在螢幕上——一個圖表資料的完整旅程，以及 Nginx、Axios、JWT 如何協同工作。

整體通訊架構

所有通訊都透過 HTTP REST API，有一個清晰的層級結構：

瀏覽器 (Vue 3)
    |
    | HTTP/HTTPS 請求（含 JWT Token）
    ↓
http://localhost:80 (Nginx 反向代理)
    |
    |── GET / → 前端靜態檔案 (dashboard-fe:8080)
    |── GET /api/dev/ → 後端 API (dashboard-be:8080)
    |── GET /api/v1/ → 後端 API (dashboard-be:8080)
    ↓
Go Backend (Gin) (8080 port)
    |
    |── PostgreSQL (5432, 5433)
    |── Redis (6379)
    └── Qdrant (6333)

Nginx 路由規則

Nginx 是整個系統的「大門」，根據 URL 路徑決定把請求轉發到哪裡：

請求 URL 轉發到 說明
/ dashboard-fe:8080 Vue 前端應用程式
/static/ dashboard-fe:8080 CSS、JS、圖片等靜態檔案
/api/dev/ dashboard-be:8080 後端 API（開發環境路徑）
/api/v1/ dashboard-be:8080 後端 API（正式環境路徑）
💡 為什麼需要 Nginx 做反向代理？
1. 統一入口：使用者只需要記得一個網址，不需要知道後端在哪個 port
2. 跨域問題解決：前端（port 80）呼叫後端（port 8080）會有 CORS 跨域問題，Nginx 讓它們看起來是同一個 host
3. SSL 終止：只需要在 Nginx 設定 HTTPS，後端服務不需要各自處理加密

圖表資料的完整旅程

以「查詢人口長條圖資料」為例，追蹤每一步：

1

使用者打開儀表板頁面

Vue Router 渲染 DashboardView.vue，元件掛載（mounted）時觸發 contentStore 的初始化方法

Vue 3 Lifecycle: onMounted()
2

Pinia Store 發起 API 請求

contentStore 調用 axios 發送請求取得儀表板資訊，以及各個元件的設定

GET /api/dev/v1/dashboard/taipei-01
3

請求經過 axios 攔截器

axios 的 request 攔截器自動在 Header 加上 JWT Token：
Authorization: Bearer eyJhbGci...

axios interceptors.request.use()
4

Nginx 轉發請求到後端

Nginx 看到 URL 包含 /api/dev/，把請求轉發到 dashboard-be:8080

proxy_pass http://dashboard-be:8080
5

Gin 路由器匹配 Handler

後端 Gin 框架接收請求，根據路由設定匹配到對應的控制器函式

router.GET("/dashboard/:index", GetDashboard)
6

JWT 中介軟體驗證身份

從 Header 取出 Token，用 JWT_SECRET 驗證簽名，解析出 userID 和 permissions，存入 context

middleware.ValidateJWT()
7

速率限制檢查

Redis ZADD 記錄這次請求，ZCARD 計算過去60秒的請求數，超過上限就拒絕

middleware.LimitAPIRequests()
8

控制器查詢資料庫

dashboard 控制器從 context 取得 userID，查詢 postgres-manager 取得儀表板設定（包含元件 ID 列表）

global.MANAGER_DB.Where("index=?", index).First(&dashboard)
9

回傳 JSON 到前端

控制器把資料格式化成 JSON，Gin 框架設定 Content-Type，回傳 200 OK 回應

c.JSON(200, gin.H{"data": dashboard})
10

前端渲染圖表

axios 收到回應，contentStore 更新狀態，圖表元件（BarChart.vue）偵測到資料變化，ApexCharts 重新渲染

computed() → watch → ApexCharts re-render

圖表資料的二次請求（取得實際數據）

取得儀表板設定後，前端還需要為每個元件分別請求圖表資料：

// 前端：為每個元件請求圖表資料
async function fetchChartData(componentId) {
  const response = await axios.get(
    `/api/dev/v1/component/${componentId}/chart`,
    { params: { city: 'taipei', timeFrom: '...', timeTo: '...' } }
  )
  contentStore.components[componentId].chart_data = response.data
}

// 後端：componentData 控制器
// 1. 從 postgres-manager 的 query_charts 表查到這個元件的 SQL
// 2. 把 SQL 送到 postgres-data 執行
// 3. 把結果格式化成前端能用的 JSON

定時刷新：資料怎麼保持最新

前端側（Polling 輪詢）

contentStore 設定定時器，每隔一段時間（根據元件的更新頻率設定）自動重新呼叫 API 取得最新資料。這稱為「Short Polling」——定期問後端「有沒有新資料？」

後端側（即時查詢）

後端不做快取，每次請求都直接查 postgres-data。因為 Airflow 已經把新資料寫進資料庫，後端只需要每次讀取最新的。

前端狀態管理的資料流向

// Vue 的單向資料流（Unidirectional Data Flow）

API 回應
  ↓
contentStore.components[id] = data // Pinia store 更新狀態
  ↓
BarChart.vue 的 computed property 重新計算 // 自動偵測響應式變化
  ↓
ApexCharts 重新渲染圖表 // 畫面更新

// 為什麼用 Pinia 而不是直接在元件裡儲存資料？
// → 多個元件可能需要同一份資料（避免重複請求）
// → 資料變化時所有訂閱的元件同步更新
💡 整體類比：把這個系統想成一個「24小時新聞台」。
- Airflow（記者）：到處採訪收集資料，定時回來交給編輯
- PostgreSQL（新聞稿資料庫）：儲存所有新聞內容
- 後端 API（播報員）：觀眾問什麼，就查資料庫說什麼
- Nginx（轉播系統）：確保所有信號正確送達
- 前端（電視螢幕）：把文字資料變成漂亮的圖表和地圖顯示
